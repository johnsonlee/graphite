## 1. Graphite 的定位

Graphite 是面向软件产物和软件系统的静态分析工具。它从程序、编译产物、资源、配置和编译器元数据中提取事实，让用户能够查询软件由什么组成、组件如何依赖、调用和数据可能流向哪里，并追溯每个结论的依据。

**单个产物和整个微服务系统都是一等使用场景。** 分析单个产物时，用户提交的输入界定了可观察范围。主线的 Explorer 拓扑把每个 `--graph` 注册项视为一个服务，现有拓扑、C4 和按 `graphId` 分组的 `/api/endpoints` 都属于兼容基线。[拓扑查询约定](topology-graph.md) · [Explorer API](../README.md#explore-resource-apis)

系统级分析将扩展这一模型。一个服务可以由多份产物描述，同一份公共库也可以出现在多个服务中。服务集合由用户指定，版本和环境由提供的证据限定。这里的“环境”指本次静态分析选用的一组配置，例如预发布环境的路由表。现有图没有系统级的服务版本或环境记录；缺少这些信息时应保留未知。

| 场景 | 用户要回答的问题 | 一个有用的答案应包含什么 |
| --- | --- | --- |
| 单个产物 | 这个 IPA 带了哪些 framework？主程序或哪个扩展声明依赖其中的支付组件？ | 包内成员及其归属、相关映像声明的依赖，以及能否根据输入确定两者的对应关系。仅发现文件随包分发时，结论止于“包含”。 |
| 整个系统 | 如果支付服务修改退款接口，哪些服务的哪些调用点可能受影响？ | 接口和调用方的服务、版本、可定位的代码或产物位置，以及协议或配置支持的关联。只引入支付 SDK 的服务与有退款调用证据的服务应可区分。 |

Universal schema 的职责，是使这些问题所依赖的事实跨输入、跨构建阶段、跨查询实现时保持含义，并使独立生成的事实能够在证据充分时一起使用。

## 2. 要解决的问题

### 2.1 语言、格式和输入边界不能一一对应

Java 和 Kotlin 都可以生成 JVM classfile；同一份 Kotlin 程序可以表现为 JVM 字节码或 Android DEX。APK 里可以同时出现 DEX、ELF 共享库和资源。IPA 可以包含主应用、扩展和各自的可执行文件；单独提交的 Mach-O 又可能有多个架构。工程目录和编译器索引则需要构建上下文才能解释。按“每门语言一种图”组织语义，会丢掉这些区别，也会让相同格式的读取工作在不同入口重复出现。

### 2.2 新事实容易在生产链路中断或变义

提取器识别了一项事实，不等于交换、保存、重新打开和查询都能保留它。主线的类字面量是一个例子：早期 JVM 图把类字面量记作整数零，后来增加的 reader 无法判断旧图中的哪个零曾经表示一个类型。另一个例子发生在 Apple 路径：一次保存曾遗漏 10,027 条枚举声明，因为它们没有对应的常量节点。已有查询样例通过，也不能证明整个事实集合都已保留。[类字面量兼容说明](webgraph-storage.md#class-literals-node-tag-16) · [Apple 枚举声明往返记录](apple-frontend-validation.md)

### 2.3 相似的观测可能支持不同的结论

“产物包含某个库”“映像声明依赖该库”“某处引用一个符号”“运行时执行了某个实现”回答四个不同的问题。高层输入也有类似差异：有默认参数时，JS 调用者显式传入的值与最终流入形参的值可以有不同来源。统一表达必须保留决定答案的区别，否则一个跨格式查询会随着输入变化而悄悄改变含义。[JS 产物的分析语义](typescript-frontend.md)

### 2.4 跨产物、跨服务关联需要依据

同名符号可以来自不同版本；同一数值地址可以属于不同架构的映像；多个服务可以使用相同的 HTTP 路径。用户需要知道 Graphite 为什么把两端联系起来，以及还有哪些候选无法排除。对微服务而言，代码中的请求、SDK 封装、服务配置和远端接口可能分属不同产物；一条只剩服务名称的依赖关系无法解释具体的影响范围。

### 2.5 缺少记录时，零结果的含义不明确

没有符号名可能因为输入经过剥离；没有调用边可能因为方法体未分析；找不到其他服务的消费者可能因为这些服务尚未纳入。本次查询因预算或取消而提前结束，又是另一种情况。需要让用户知道，缺口出现在输入、构图、系统覆盖还是查询执行。Graphite 已有的方法体分析范围和跳过原因，是这项要求的现有基础。[分析完整性说明](analysis-completeness.md)

## 3. 目标

1. **保留主线已支持的工作流和查询语义。** 支持范围以主线 README 为准，涵盖各前端与输入（含 Spring Boot 和 WAR 的嵌套 JAR、Swift 和 Objective-C）、`graphite import`、图目录与 `.graphite` 归档，以及 Kotlin 库 API、原有 Kotlin 查询引擎、Rust 引擎、REST、MCP 和 Explorer。保留各入口的选项、扫描边界、公开标识、API 和缺失值语义。新 reader 应能读取旧图；已有事实经导入、保存、重开后仍可查询。已有 Cypher 结果默认保持一致。如需有意修正语义，须明确声明变化及受影响的查询，并按回归门禁评审精确的变更前后预期。#226 修正了类字面量的建模；旧图已经丢失的信息仍需从原始输入重新提取。[主线支持范围](../README.md) · [语义变更验收](benchmark-regression-gate.md) · [类字面量兼容说明](webgraph-storage.md#class-literals-node-tag-16)
2. **让新的输入格式可以独立接入。** 新格式应当能引入其原生概念，也能复用已有概念。接入的主要成本应落在理解新格式和提取其事实；常规扩展应避免迫使所有存储、查询和展示实现同步发布。旧 reader 打开新图时，只能在能正确解释相关事实时回答查询，否则应明确拒绝该查询或整张图。验证时应包含会遇到新标签的查询；例如旧 reader 遇到 `ClassConstant` 的 tag 16 可以报错，把该记录跳过并返回零个匹配则会给出错误答案。判断“支持 ELF”或“支持 Mach-O”时，应说明可回答的是成员清点、装载依赖、符号、源码对应还是调用分析。
3. **让同义问题获得一致答案。** 对不同格式都能提供的事实，用户应能提出同一个问题并按同一含义解释结果。查询 ELF 或 Mach-O 的链接依赖就是一例。需要格式细节时，用户仍能查看各自的原始依据；涉及特定语言语义时，保留该语言的精度。
4. **支持系统级分析并保留局部归属。** 用户应能从单个符号或调用点追到它所属的产物，并在证据充分时确定所属服务和版本，也能从某项接口变更反查系统内可能受影响的位置。服务清单不全、所选环境配置不同或路由有歧义时，系统级结论应保留这些限定。
5. **让完整性声明可检验。** 清楚区分直接观察、分析推导和未知，说明输入范围、事实种类和执行完成情况。“指定范围内没有匹配项”应当有完整检查作依据；存在未覆盖范围时，仍应能利用已确认的局部结果。

## 4. 非目标

- **无损归档和逐字节重建输入。** Graphite 可以记录原件身份和证据位置。程序图无需重建一个字节级相同的 JAR、IPA 或 ELF。ZIP 压缩参数之类的细节，只有在它们影响已承诺的分析问题时才进入范围。
- **穷尽每种格式，或让所有格式具备相同的分析深度。** 读取一个 stripped ELF 的装载依赖可以是一项完整能力，即使本地函数名不可得。支持某种输入不自动承诺建模每个格式字段、恢复所有指令语义或提供源码级数据流。
- **完整恢复源码、作者意图或唯一调用图。** 优化、内联、类型擦除、混淆和剥离都会改变可观察信息。缺少调试信息、符号或解析上下文时，可以保留多个候选或未知结果。
- **建立覆盖所有语言的完整编译器 IR。** 公共语义以 Graphite 要回答的程序问题为边界。语言独有的概念可以保留自身含义，无需强求 JVM、Swift、JS 和机器码之间处处对应。
- **仅凭静态输入还原运行时全貌。** 随包组件、潜在调用和所选环境配置支持的服务关联属于静态分析范围。配置说明某条路由适用于哪些条件。某个时刻实际部署的实例、一次请求经过的路由，以及实际执行的目标，需要相应的部署或运行时证据。

## 5. 如何评审后续方案

评审一项拟支持的能力时，先写出用户的问题、答案所需的证据，以及何时有资格给出否定结论。下面三个问题可以作为共同尺度：

- **老用户是否失去已有答案？** 用同一批已支持的输入、选项和旧图，核对完整事实与公开查询结果，包括没有对应节点的元数据和未采集时的行为。有意变更的结果逐项核对已评审预期；另用旧 reader 打开带有新事实的图，核对正确答案或明确拒绝。
- **新输入能否独立产生价值，也能补充已有分析？** 单独提交一份 Mach-O 时，应能利用其自身证据；后来增加匹配的 dSYM 时，应能解释新增了哪些源码关联。把同一 ELF 独立提交和放入 APK 时，其内容事实应一致，包内归属应可辨。
- **全系统查询能否给出可行动且不过度推断的答案？** 对退款接口变更，应能定位有证据的调用方，也能指出哪些服务、版本或通信路径尚无充分证据。“已分析的 18 个服务中找到 2 个调用者”只有在系统边界和相关覆盖都得到确认后，才支持“整个系统只有 2 个调用者”。

保存安全、损坏检测、查询取消与预算、分页和代表性多图负载下的性能，仍有各自的工程验收要求。本文为这些工作明确需要保住的语义；物理格式、索引布局、API 和迁移步骤留待方案阶段决定。[仓库验收约定](../CONVENTIONS.md)
