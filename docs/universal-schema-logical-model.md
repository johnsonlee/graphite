# Graphite universal schema: Draft logical model

English | [简体中文](universal-schema-logical-model.zh.md)

Design review draft. The [product scope agreed in #231](universal-schema-scope.md) governs this proposal. The compatibility baseline is the [README at 70f908cf](https://github.com/johnsonlee/graphite/blob/70f908cf6acf4b80ce74d038cecba07f119a544b/README.md). The names below describe logical roles. Cypher labels, file formats, indexes and network APIs are separate design decisions.

## 1. Start with the program questions Graphite must answer

**Preserving the full supported scope is the first acceptance condition.** Take a JAR with two overloads of `radixSort`, one taking `byte[]` and the other `byte[][]`. A user who can distinguish those declarations today must still find both after saving and reopening the graph. Their owners, descriptors and public query results must survive the round trip. The same obligation applies across the supported inputs and interfaces in §4. An intentional semantic change requires the explicit review defined in #231.

**Single-artifact and whole-system analysis are both first-class use cases.** Production deployments already use cross-graph Cypher and topology rules to locate dependencies between services. A service maintainer changing the payments refund API needs to find the call sites that could be affected across the system. Two services may package the same SDK. Attributing a refund call to one of them requires evidence from its code and from the routing configuration for the selected environment. Reporting that no other service calls the API also requires knowing which services and calls the analysis covered.

Those questions determine the model. Each graph publishes scoped objects and facts with evidence. A system view connects facts across selected graphs under explicit conditions while preserving their original identities. We first check that model against supported inputs, including the production cross-graph API and topology (§3–4). We exercise the proposed stronger binding and coverage rules in §6, then use prospective IPA, ELF and Mach-O inputs to test its extension boundaries (§7). The explicit references and namespaced definitions in #169 are one way to express the model. Physical design is a later decision. [Earlier prototype #169](https://github.com/johnsonlee/graphite/pull/169)

## 2. Objects and identity in the existing program graph

A snapshot identifies one concrete output, including its local node numbering. Each stored node is an occurrence addressed by (snapshot, NodeId). Equal property values alone cannot merge occurrences. Metadata rows use their own keys within the snapshot. A declared JVM method is keyed by its declaring class, name and full descriptor, including the return type. In Hive’s `shaded.parquet.it.unimi.dsi.fastutil.bytes.ByteArrays`, the keys end in `radixSort([B)V` and `radixSort([[B)V`. The array ranks distinguish these declarations. The existing display signature omits the return type and remains available as a projection. [MethodDescriptor and node types](../frontend/jvm/core/src/main/kotlin/io/johnsonlee/graphite/core/Node.kt) · [Hive classfile audit](declared-types-corpus-identity-audit.md)

| Existing query family | Objects, edges and metadata retained in the snapshot |
| --- | --- |
| Dataflow | `IntConstant`, `LongConstant`, `FloatConstant`, `DoubleConstant`, `BooleanConstant`, `StringConstant`, `NullConstant`, `EnumConstant`, `LocalVariable`, `FieldNode`, `ParameterNode` and `ReturnNode` retain their node IDs and typed properties. A `DataFlowEdge` records its directed endpoints and flow kind. An enum declaration has a separate (enum class, case name) key and an ordered list of constructor values, even if it has no constant node. |
| Class literals | A `ClassConstant` is a value occurrence whose `value` is the referenced JVM type descriptor. A string constant containing the same descriptor and an integer zero in a legacy graph keep their original kinds. |
| Call graph | Each `CallSiteNode` has its own ID, caller, callee, optional receiver, and ordered argument references. Distinct sites can share `callee_name`; the existing Cypher patterns accept both `CallSiteNode` and `CallSite`. A `CallEdge` records directed endpoints and virtual/dynamic flags. The method inventory includes declarations with no incoming calls. |
| Type hierarchy | Snapshot-local type names identify entries in the hierarchy. A hierarchy fact records subtype, relation (`EXTENDS` or `IMPLEMENTS`) and supertype; a `TypeEdge` preserves the relation on its node endpoints. Preserve class origin and declared-type bindings when recorded. |
| Annotations | An `AnnotationNode` is an occurrence with its own ID and typed attributes. The member lookup uses class name and member name, then annotation name. This lookup alone cannot identify a particular overload. |
| Lambda and method-reference dispatch | Preserve the observed site and any derived site as separate occurrences. JVM call-site ordinals, when recorded, distinguish sites of the same caller and callee. Derived ordinals are negative; an available origin points back to the originating site. |
| Resources | `ResourceFileNode` and `ResourceValueNode` retain their IDs, paths and recorded source, profile, key or typed value as applicable. Resource inventory entries retain path and source, and the accessor resolves paths within its snapshot. A `ResourceEdge` retains its endpoints and relation, such as `OPENS` or `LOOKUP`. |

For every recorded edge, preserve direction, endpoint identities, kind and kind-specific payload. The fifth edge family, `ControlFlowEdge`, can carry a branch comparison. Branch scopes are retrieved by condition node ID and local definitions by local node ID. Other metadata keeps its recorded lookup keys, including class origin by class name, synthetic identity by member key and weighted artifact dependencies by ordered artifact pair. [Edge types](../frontend/jvm/core/src/main/kotlin/io/johnsonlee/graphite/core/Edge.kt) · [Graph metadata accessors](../frontend/jvm/core/src/main/kotlin/io/johnsonlee/graphite/graph/Graph.kt) · [Resource inventory](../frontend/jvm/core/src/main/kotlin/io/johnsonlee/graphite/input/ResourceAccessor.kt)

**Snapshot identity and build provenance answer different questions.** For each producer run, record the input digests, effective options and producer name and version. Equal provenance permits comparison of build conditions. Even with identical inputs and options, a producer upgrade or a repeat run can assign node 7 to a different declaration. Reuse a local reference across copies only when their concrete output identity, including the identifier assignment, is established. Whether two outputs came from the same build execution requires a recorded run identity or equivalent evidence. An imported legacy graph can have its own snapshot identity while its original build or producer remains unknown. A registry name can refer to different snapshots over time.

## 3. Existing relationships, metadata and query projections

### 3.1 Relationships in existing graphs

For each edge, preserve the snapshot, stored source and target, family, subkind or flags, and the multiplicity exposed by the graph. For metadata, preserve the declaration or entry independently of whether any edge visits it. The five edge families below are present in both the JVM model and Graph IR. The spellings in a Cypher pattern and the value of an edge’s `kind` can differ. [JVM edges](../frontend/jvm/core/src/main/kotlin/io/johnsonlee/graphite/core/Edge.kt) · [Graph IR](../ir/graphite_ir.proto) · [Cypher relationship matching](../backend/cypher/src/engine/matching.rs) · [Decoded edge names](../backend/storage/src/graph.rs)

| Family and public pattern names | Direction and meaning to preserve |
| --- | --- |
| `DATAFLOW`, `DATA_FLOW` | Follow the recorded producer → consumer direction. Preserve `ASSIGN`, `PARAMETER_PASS`, `RETURN_VALUE`, `FIELD_STORE`, `FIELD_LOAD`, `ARRAY_STORE`, `ARRAY_LOAD`, `CAST` and `PHI`. A `ClassConstant` flowing into a call keeps its descriptor-valued `value`. The call’s ordered argument slots and receiver remain separately queryable even if two slots reference the same node. |
| `CALL` | Preserve both endpoints and the virtual and dynamic flags. Caller and callee descriptors belong to the call site. For example, the JVM frontend can emit a dynamic self-edge on a lambda implementation call site whose callee descriptor identifies the target. Replacing it with an edge to a new member changes an existing traversal. [JVM call-site emission](../frontend/jvm/sootup/src/main/kotlin/io/johnsonlee/graphite/sootup/CallSiteEmitter.kt) |
| `TYPE` | `EXTENDS` and `IMPLEMENTS` run from subtype to supertype. Preserve hierarchy metadata keyed by subtype, relation and supertype even when the declarations have no corresponding edge endpoints. |
| `CONTROL_FLOW`, `CONTROLFLOW` | Preserve the directed `SEQUENTIAL`, `BRANCH_TRUE`, `BRANCH_FALSE`, `SWITCH_CASE`, `SWITCH_DEFAULT`, `EXCEPTION` and `RETURN` edges. A conditional edge can run from a condition operand to a node in the selected branch. Its comparison operator and comparand reference, branch membership and statement-ordered local definitions carry information that adjacency alone cannot recover. |
| `RESOURCE` | The five kinds `OPENS`, `LOADS`, `BUNDLE_CANDIDATE`, `LOOKUP`, `ENUMERATES` have Cypher types `RESOURCE_OPEN`, `RESOURCE_LOAD`, `RESOURCE_BUNDLE_CANDIDATE`, `RESOURCE_LOOKUP`, `RESOURCE_KEYS`, respectively. Preserve the stored direction, e.g. resource file → reader call site. Keep file and parsed value records with their existing paths, keys, values and qualifiers. The README also describes `RESOURCE_CONTAINS` (file → value). It has no corresponding kind in the current IR or matchers. Track that documentation gap separately and preserve the actual result of the existing query. [Resource queries](../README.md#query-resources-with-cypher) · [JVM matcher](../frontend/jvm/cypher/src/main/kotlin/io/johnsonlee/graphite/cypher/RelationshipPatternMatcher.kt) |

The legacy projection also exposes method declarations, enum-case values, class origins, weighted artifact dependencies, and annotations with their declaring class, member, annotation name and value map. A method can have zero callers, an enum case can have an empty value list, and a class-level annotation can have `<class>` as its member. A class literal is a typed constant and lambda dispatch can be represented by a call site and its recorded flows. None of these facts requires an extra relationship family. [What the graph captures](../README.md#what-the-graph-captures) · [Node definitions](../frontend/jvm/core/src/main/kotlin/io/johnsonlee/graphite/core/Node.kt) · [Metadata batches](../ir/graphite_ir.proto)

### 3.2 Shared vocabulary and public aliases

Adopt the architecture proposal’s `Module`, `Type`, `Member`, `CallSite`, `Constant`, `Local`, `Parameter`, `Return`, `Annotation`, `Resource` and `ResourceValue` as logical roles. A JVM method, JavaScript function or Swift initializer can occupy the callable-member role while keeping its frontend’s declaration key and signature grammar. A JVM invocation, JavaScript call and Objective-C message send can each supply a call site. A decorator or attribute projects to annotation metadata only to the extent its frontend records the attachment and values. Shared roles do not imply equal extraction coverage. [Architecture proposal §3](architecture-frontend-backend.md#3-the-graph-model)

Keep public labels such as `CallSiteNode` and `CallSite`, typed constant labels, and each frontend’s existing property and `keys(n)` behavior. For example, `MATCH (n:CallSiteNode) RETURN n.callee_name LIMIT 10` reads the name in the stored callee descriptor without resolving a member. The proposed `callee.owner/name/signature` and `caller.owner/name/signature` roles map to the existing `callee_class/name/signature` and `caller_class/name/signature` properties (prefix repeated for each property). Preserve the `class` owner on fields and annotations, `enum_type` on enum constants, `method` on locals, parameters and returns, and `static` on fields. Keep the existing graph-specific representation of signatures and descriptors. These mappings describe logical roles and do not add keys to existing query responses. [Public query example](../README.md#cypher-compatibility) · [Current property projections](../backend/cypher/src/engine/props.rs)

The proposal’s first-class Type and Member nodes, Module → Type → Member containment, `CONFORMS` and `ALIAS`, expanded dispatch flags and language-specific properties can extend an explicitly selected view when supported by evidence. The existing graph keeps its original node counts, virtual Method view, edge endpoints and flags. This model adopts the families and their meanings without prescribing the proposal’s 8-bit encoding or universal physical indexes.

### 3.3 Existing production paths: cross-graph queries and service topology

Graphite already executes a single cross-graph Cypher query over a selected graph set. With `graphs: ["orders", "billing"]`, `POST /api/cypher/graphs` joins and aggregates over the union by default. Explicit `fanout` executes the query independently in each graph. The results, row limits and graph attribution of both modes are part of the compatibility baseline. [README API contract](https://github.com/johnsonlee/graphite/blob/70f908cf6acf4b80ce74d038cecba07f119a544b/README.md#L1261-L1272)

```cypher
MATCH (a:IntConstant {value:42}), (b:IntConstant {value:17})
RETURN DISTINCT graphId(a) AS callerGraph, graphId(b) AS otherGraph
```

We built two JARs with the released Graphite 2.18.0. In orders, a method calls `com.company.rpc.billing.Adapter.refund(42)`. In billing, a method returns 17. Sending the query above against both saved graphs in the default mode returned one row, `(orders, billing)`, with `$metadata.graphIds` equal to `["billing","orders"]`. Sending the same request in fanout mode returned zero rows.

For service topology, the existing README `--topology` rule takes the caller from `graphId(call)` and the target service from the adapter class name. On the same inputs the production server’s `/api/topology` returned one orders → billing edge with protocol `company-rpc`, operation refund, weight 1 and the adapter class name as evidence. Section 6 separately tests the proposed conditions for unique targets and complete caller counts. Existing cross-graph queries and topology rules operate independently of those additional conditions. [README RPC rule](https://github.com/johnsonlee/graphite/blob/70f908cf6acf4b80ce74d038cecba07f119a544b/README.md#L948-L965)

### Cost contract for ordinary queries

**Cost is part of the compatibility contract.** Existing Cypher, REST and MCP queries that request ordinary rows keep their result and cost contract. A call-site lookup or dataflow traversal must be executable using the baseline facts alone, with no mandatory evidence joins, coverage aggregation, construction of a system view, or cross-snapshot resolution during loading or querying. An explicit request for evidence, a scoped absence proof or a system-wide binding can require those operations. Honor existing cancellation, work budgets and error behavior on both paths.

Judge a proposed implementation in repository priority order: correctness first, availability and stability next, then server query p50 and p95, then build and save. Exercise ordinary queries on real, representative multi-graph requests with matched scope, cache state, concurrency and fully consumed results. Compare p50 and p95 per case, including absolute milliseconds, and check CPU, RSS and heap limits for each affected operation. Hosted gate timings are report-only. The logical requirement is zero additional mandatory work for the optional features; latency and resource acceptance require measurements. ## 5. Additional context and evidence for queries

### Optional context for artifacts and systems

Existing graphs can answer the questions above without a container hierarchy, mapped addresses or a service inventory. These objects add context when the input supplies it. Named linker symbols can lack a body, code ranges can lack a name, and a declaration can have several code instances.

| Logical object | Identity and relationship constraints | Question it helps answer |
| --- | --- | --- |
| Artifact content and member (Artifact, Member) | Content can be a file or a collection with an inventory. Each member occurrence has its own identity, one parent container, a member name and the content it refers to. Occurrence positions distinguish entries with the same name. Matching digests obtained with the same algorithm can establish content equality. When content identity is unavailable, retain only a local reference. | Which two applications package the same library? Can we reuse facts about the same ELF supplied directly and extracted from an APK? |
| Representation | An interpretation of content within a particular input scope and context. It can depend on several inputs, such as a compiler index, source and build target. One file can yield multiple representations, such as two Mach-O slices. Facts obtained by parsing content can be reused by content identity. Conclusions that depend on search paths or compilation targets also carry that context. | Why can declarations from the same Swift source file compiled into two modules have distinct identities? |
| Location | A representation, a coordinate system, an owner where needed, and a point or half-open interval. The coordinate system defines the unit and origin. Examples include bytecode offsets within a method, byte offsets within a section, file offsets within a slice, and link-time virtual addresses within an image. A mapping between coordinate systems is itself a fact. A location can have several counterparts or none, and a mapping can cover only part of its domain. | Which image owns this address? Can we locate it in a file or in source? |
| System view (SystemView) | An explicit service inventory, selected snapshots, service versions where known, and static environment inputs. Evidence-backed attribution connects services to artifact members or representations. One service can correspond to multiple graphs, and the same content can appear in multiple services. Unknown versions stay unknown. | To which set of services and which environment does the conclusion apply? |

**A direct identity join is valid only within the identity's scope.** Node 7 in one graph and node 7 in another are distinct references, as are address 0x1000 in two different images. Names, deobfuscated display text and URL paths provide clues for matching. A cross-snapshot association must state its kind. “Contains identical bytes” supports content reuse, “debug information describes this image” supports source association, and “can bind to this API under this configuration” supports impact analysis. None of these associations automatically merges nodes. Existing public identifiers keep their original query projection for legacy graphs.

### 5.1 Fact identity and evidence

In the following notation, parentheses contain named roles and brackets denote ordered sequences. The notation is for reviewing the model and examples.

```text
Definition = (namespace, name, semantic version, type and cardinality of each role, equivalence and coverage conditions)
Fact       = (definition, scope, role values)
Evidence   = set of bases supporting the fact
Basis      = direct observation(extraction run, optional locator within input)
           | derivation(rule and version, references to premise facts, interpretation context)
```

- **Roles and values.** A role can be required, optional or repeated. Its definition specifies whether repetition and order are significant. Values include typed scalars, explicit nulls, object or fact references, and structured collections. The definition determines equality and precision. A missing field, an explicit null, an empty sequence and a fact that was never extracted each have distinct meanings. Two arguments of a call can refer to the same value. Facts with the same endpoints can differ by role, ordinal or occurrence.
- **Fact identity and evidence.** A definition specifies which scoped role values identify the claim, including occurrence or ordinal where significant. Two independent observations supporting the same claim contribute two bases to one fact. A fact reference can use this logical identity. A batch can declare a default set of bases for all its facts. A fact can add to that set or override it with its actual bases. A locator, when known, can identify a table entry, member path, source range or legacy graph record. A legacy record attests to what the graph recorded even when its original source location is unknown. These rules permit shared evidence without requiring a stored identifier, evidence record or locator per fact.
- **Counting and conflicts.** Count call sites by distinct site identity and evidence by distinct basis. Trace rule conclusions to premise facts and ultimately observations, including where program relationships form cycles. Preserve conflicting observations with their sources and contexts. A query requiring a unique conclusion remains unresolved while the conflict affects the result.
- **References and resolution.** Record the observed reference even when no target is known. Each candidate names the rule, context and evidence that make the target possible. Confirm a unique binding only when evidence establishes the complete candidate domain under that rule and context, the required matching and precedence conditions have been evaluated, and exactly one viable target remains. Retain the supporting facts and coverage claim so the result can be checked. A lone observed candidate in an open domain remains a candidate.
- **Evolution.** A new format can publish definitions and declare evidence-backed projections onto common definitions. Within one definition version, role meanings, identity and result precision must remain stable. Changing “explicit argument” to “effective argument” requires a separate definition. The old projection keeps its semantics. A generic consumer can interpret structure and references. Specific type inference requires the corresponding capability. A reader must explicitly reject the operation or the graph when a fact it cannot interpret could affect the answer.

### 5.2 Optional relationships for additional inputs and system views

These illustrative definitions apply only when a view supplies the corresponding evidence. Existing graphs and queries require none of them. Domains retain native predicates such as ELF dynamic table entries and Mach-O load commands.

| Relationship (illustrative) | Meaning |
| --- | --- |
| `contains(parent, member, content)` | The content occurs in this parent container. Member identity preserves ownership. |
| `declaresDependency(image, requestedLibrary)` | The image's load metadata requests the library and can retain its original name and qualifiers. A binding relationship expresses whether the request resolves to a particular member. |
| `refersTo(site, reference)`, `candidate(reference, target, context)` | Distinguish a reference observed in the input from a possible target identified during resolution. |
| `confirmedBinding(reference, target, context)` | The resolution rule selects exactly one viable target in its covered candidate domain. The conclusion applies under the recorded conditions. |
| `argument(call, ordinal, value, role)`, `flowsTo(value, use, context)` | Argument order and origin have evidence. Dataflow preserves the analysis boundaries and does not directly connect a client value to a parameter in another service. |
| `provides(serviceRevision, operation, handler)`, `requests(site, operationRef)` | API declarations and client operations can be queried independently. Cross-service binding requires matching evidence such as the protocol, target and route. |
| `corresponds(left, right, kind, context)` | The kind of association determines which conclusion it supports. Source, indexes, images and debug records can correspond many to many. |

### 5.3 Empty results, partial results and query boundaries

A coverage claim applies to **(snapshot or system inventory, fact definition and version, selected scope, extraction conditions)**. A claim can cover a batch with exceptions for narrower scopes. Complete means enumeration finished for the particular question. Partial means the checked scope is known and gaps remain, even if the checked portion yielded zero matches. Unknown means no sufficient claim is available. The presence of a node kind cannot establish coverage across a graph. Record which run collected the facts, why extraction skipped a scope, or where data was damaged, as applicable. When data declared necessary is corrupt, affected queries return an integrity error.

For a query that asks for a completeness claim, determine its object domain and required facts, then combine coverage across the relevant scopes. A positive match can be reported with its evidence. Counts in the presence of gaps describe only the confirmed set. Negation, exact counts and unique bindings require coverage of every scope and resolution candidate that could change the answer. Check complete consumption of the query results separately. Cancellation or exhaustion of a work budget cannot establish zero matches. Existing Cypher contracts for rows, nulls and errors continue to apply. These conditions govern when a conclusion holds. How an API conveys them is a separate decision. [Existing method-body completeness semantics](analysis-completeness.md)

## 6. Cross-service query: who could a refund API change affect?

The system view selects one revision of each service. Both orders and billing package the same SDK. Two call sites in orders request `POST /refunds` through the alias `pay`. At B2 in billing the operation is known, but the destination expression could not be resolved. The inventory includes legacy-worker, whose requests were never collected. The question is which services have a statically bound call to the payments handler H1 under staging.

The example fixes the protocol, verb and path to HTTP `POST /refunds`. Every listed request has independent call-site evidence. SDK membership supplies none. A route entry enumerates **all** applicable destinations for that environment and alias. A provider entry enumerates **all** handlers for that service revision and operation. An empty set certifies no match in that scope. An absent entry leaves the scope unknown. A partial extraction with known candidates must retain those candidates as evidence and leave enumeration open. The small fixture below uses complete entries or missing entries.

The resolver has one deterministic rule: follow the selected alias and match the operation at its destinations. Its declared scope excludes fallback routes, rewrites and runtime overrides. A definite binding requires a known request, complete applicable routing and provider evidence, and exactly one admissible handler after applying all rules. The basis for that binding identifies the site, matching route and provider entries, their coverage claims and the rule applied. Ambiguous candidates remain visible. A missing fact that could change the answer leaves the site unresolved. Production resolvers must establish these conditions from their own rules and coverage. [Binding and counting acceptance cases](../examples/universal-schema/logical-model.doctest)

| Condition | Conclusion for payments/H1 |
| --- | --- |
| Complete staging routes and provider inventory bind C7 and C8 uniquely to H1 | Two confirmed sites belong to one service, orders. B2 has an unknown destination and legacy-worker has uncollected requests, so the total service count is unknown. |
| C7’s applicable route table or the destination’s provider inventory is missing | C7 is unresolved. A complete route table with zero destinations excludes C7. |
| Two applicable routes lead to H1 and H2 | Retain both candidates. Even if only H1 has been observed, C7 remains unresolved while the other destination’s provider inventory is missing. |
| B2 resolves to sandbox-pay and completing request collection adds no sites | With a complete service inventory the exact count is one. With an open inventory only the lower bound of one is established. |
| Only orders is in scope in test, where the route leads to sandbox-pay | The exact count for that scope is zero. Adding the unexamined legacy-worker leaves zero confirmed and the exact total unknown. |

The existing topology runs rules over the configured graphIds, aggregates weights by (source, target, protocol) and deduplicates operation and evidence. The call-site results above can be projected onto service pairs while retaining the detailed evidence for inspection. Existing rules keep their original weight calculations. Each graph registered through the legacy workflow still maps to one service. C4, topology and endpoints grouped by graphId retain their existing contracts. Establishing field-level dataflow across services also requires evidence about serialized fields, protocol versions and the peer’s decoding map. An endpoint match alone supports only operation-level impact. ## 7. Three boundaries illustrated by native samples

### IPA and Mach-O: membership, load requests and candidate bindings

We built an arm64 iOS executable named Demo and a dynamic library named Pay in a temporary directory. Demo’s C entry point references the external function `pay`, which the library defines. We put both binaries in a ZIP with an IPA member layout. The following observations come from independent tools. We checked package layout and static metadata only. We did not install or execute the sample. [Apple QA1798, Checking Distribution Entitlements (IPA inspection example)](https://developer.apple.com/library/archive/qa/qa1798/_index.html)

| Tool observation | Fact in the model |
| --- | --- |
| `unzip -Z1 demo.ipa` lists `Payload/Demo.app/Demo` and `Payload/Demo.app/Frameworks/Pay.framework/Pay`. | Two member occurrences, each with its own content and image representation. |
| `otool -l` on Demo shows `LC_LOAD_DYLIB @rpath/Pay.framework/Pay` and `LC_RPATH @executable_path/Frameworks`. | The main image declares a dependency and supplies its own search condition. Its separate load request for a system library can remain an external reference. |
| `otool -D` on Pay gives the same install name. Its `nm -gU` output includes a definition of `_pay`. Demo’s `nm -u` output includes an undefined `_pay`. | The search condition, member location, architecture and library identity support a static candidate. The symbol reference and export each stand on their own. The two symbol tables alone cannot locate a call site or establish execution. |

**Counterfactual checks.** If Pay is removed from the package, Demo still declares its load request and the packaged candidate disappears. Adding a framework that matches none of Demo’s load requests can add facts about the framework and its package membership. Demo’s candidates stay the same. In a multi-architecture Mach-O, arm64 and x86_64 each have their own address domain and build UUID. Matching a dSYM by architecture and UUID adds source associations only to the corresponding slice. A matching filename with a different UUID cannot establish a binding. The last two cases follow from the specification. [Apple’s build UUID and dSYM rules](https://developer.apple.com/documentation/technotes/tn3178-checking-for-and-resolving-build-uuid-problems)

### ELF: one number can denote two kinds of location

We compiled the same Demo source to an AArch64 ELF object. `readelf -h` reported ELF64 and type REL. `readelf -Ws` showed a defined main and an undefined pay. `readelf -rW` showed an R_AARCH64_CALL26 relocation referencing pay at offset 0x10 in .text. The answer is “this object has a relocation reference to pay at .text+0x10.” Here `readelf -SW` places .text at file offset 0x40. Section offset 0x10 therefore identifies file byte 0x50, while file offset 0x10 identifies a byte in the ELF header. The number 0x10 needs a coordinate domain as well as an object identity. This sample supplies neither a dependency library name nor a final load address. [ELF relocation specification](https://gabi.xinuos.com/elf/06-reloc.html)

Consider two further cases for a loadable ELF. If a PT_LOAD segment has file size 0x100 and memory size 0x180, segment-relative offset 0x120 falls in its zero-initialized region. It has an image location with no corresponding file byte. If the same shared library is supplied as a standalone file and as an APK member, its content should yield the same dynamic dependency requests. Which library a request resolves to still depends on the selected search context. Local function names can be unknown in a stripped input while fully read dynamic dependencies remain queryable. [ELF loading specification](https://gabi.xinuos.com/elf/07-pheader.html)

## 8. Review conclusions and open questions

The baseline cases require independent declarations, value roles and coverage by fact family. The multi-service query requires attribution, environment, evidence for the applied rules and inventory completeness within its scope. The native samples require a coordinate domain for each location and separate facts for membership, references and bindings. Each constraint can be tested by observing how the answer changes.

This review checked existing repository cases, inspected native samples with independent tools and ran the multi-service relational example above. These checks establish what the logical model can express. Implementation acceptance still needs real multi-bundle IPAs, paired extraction from universal Mach-O binaries and their dSYMs, stripped ELF shared libraries and end-to-end compatibility of production queries. Reviewers should test whether the identity and coverage conditions for each common predicate are precise enough, and whether the evidence available in each domain can satisfy the confirmed-binding rule in §5.1. The refund case in §6 exercises that rule for one routing model. Other domains may still need their own predicates and resolution rules.
