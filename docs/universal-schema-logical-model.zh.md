# Graphite universal schema：现有问题与逻辑模型

[English](universal-schema-logical-model.md) | 简体中文

本设计评审稿遵循 [#231 议定的产品范围](universal-schema-scope.zh.md)。Graphite 从软件产物和系统中提取静态事实并建立关联，让用户能够研究程序结构、依赖、调用与数据流。首要要求是保留目前支持的全部输入与公开行为。全系统分析，包括已投入使用的跨图查询，也在这条基线之内。对其他输入格式的扩展以此为基础。具体保留什么信息，由 Graphite 承担的分析问题决定。要求完整保留提取出的事实，并不要求记录输入的每个细节、逐字节重建输入、实现通用编译器 IR，或推断运行时实际执行了什么。对于有意修正的既有行为，须依照 #231 明确评审变更前后的差异。

公开兼容性基线仍是 [70f908cf 的 README](https://github.com/johnsonlee/graphite/blob/70f908cf6acf4b80ce74d038cecba07f119a544b/README.md)。下文对现状的诊断依据 `d51abb5c` 的代码，并分别标明历史故障、当前代码行为及由源码推断的风险。README 与已发布行为不一致时，须将两者一并记录为契约缺口。本提案既不假定文档所述能力已实现，也不静默删除已承诺的能力。解决缺口需要明确修正行为或文档。本提案选择逻辑契约，文件编码、索引、传输 API 和迁移机制留待后续设计。[原型 #169](https://github.com/johnsonlee/graphite/pull/169) 与[前后端架构提案](architecture-frontend-backend.md) 提供参考，不限定解决方案。

## 1. 现有实现

当前有三条用于生产的构图路径。此外，显式导入 IR 和重新打开已保存的图也是支持的入口。

| 路径 | 实现 | 对共享契约的影响 |
| --- | --- | --- |
| JVM 与 Android | `JavaProjectLoader` 构建 Kotlin Graph，随后由 `GraphStore` 保存。APK 有专门的 DEX 输入路径；classfile 与 DEX 的声明已经共用一套声明类型处理逻辑。 | 这些输入不经过 Protobuf IR。Kotlin 图新增的能力不会自动出现在该 IR 中。 |
| Swift 与 Objective-C | Apple 前端读取编译器索引、源码及选定的资源，输出 Protobuf Graph IR，再调用 JVM 导入器和写入器。 | 一项事实要进入最终保存的图，编译器模型、IR 和 Kotlin 图都要能表达它。 |
| JavaScript 产物 | Web 分析器输出 JSON 交换数据，由 Rust 导入器校验并保存。 | 这条路径有自己的封闭节点类型集合及字段映射。TypeScript/JSX 必须先编译成支持的 JavaScript 产物。 |

相关实现见 [JVM 构图](../frontend/jvm/query/src/main/kotlin/io/johnsonlee/graphite/cli/BuildCommand.kt)、[输入选择](../frontend/jvm/sootup/src/main/kotlin/io/johnsonlee/graphite/sootup/JavaProjectLoader.kt)、[Apple 分派](../cli/src/build.rs)、[Web 分派](../cli/src/build_ts.rs)、[Protobuf IR](../ir/graphite_ir.proto) 和 [JSON 导入器](../backend/storage/src/interchange.rs)。

扩展需要同时考虑输入格式与分析能力。Java 和 Kotlin 可以共用 classfile 读取器，Kotlin 也可以 DEX 形式提供。一个 APK 可以包含多种格式，而解释编译器索引可能还需要源码与编译上下文。单凭语言名称不能确定统一的解释方式。

程序模型的内容多于节点和边。Kotlin 除了公开节点的每次出现以及五类边，还分别公开方法、类型层级、枚举声明及构造参数值、类来源、注解、分支作用域、局部定义、声明类型和分析完整性。持久化时需要通过不同的访问接口收集这些内容。JVM 和 Rust 的读取器与查询引擎分别解释保存下来的记录；公开的 Cypher 属性和 Explorer JSON 还有各自的映射。[Graph 契约](../frontend/jvm/core/src/main/kotlin/io/johnsonlee/graphite/graph/Graph.kt) · [元数据收集](../frontend/jvm/webgraph/src/main/kotlin/io/johnsonlee/graphite/webgraph/GraphMetadataCollector.kt)

Graphite 已能在所选图的并集上执行一条 Cypher 查询，支持连接、过滤、聚合，并为每行结果保留图来源。显式选择 fanout 时，每张图分别执行查询。已有拓扑规则可以从这些图推导服务依赖，Explorer 的既有流程使用注册图标识一个服务。这些能力都需要保留。尚待建模的是，来自不同生产者的产物、服务版本与配置，如何共同为系统级查询结果提供依据。[跨图 API](../README.md#mcp-integration) · [拓扑契约](topology-graph.md)

## 2. 问题及成因

### P1. 同一项事实有多份独立维护的定义

`ClassConstant` 已存在于 Kotlin 节点模型、持久化记录、Rust 读取器及 JSON 导入器中。Protobuf IR v1 却没有对应的变体，它的 CallSite 消息也没有调用点序号及来源字段。因此这份 IR 无法完整交换当前 JVM 图中的信息。由此可以确认各条路径的表达能力不一致；并无证据表明 Apple 目前会产生这些事实，随后又把它们丢掉。[节点模型](../frontend/jvm/core/src/main/kotlin/io/johnsonlee/graphite/core/Node.kt) · [记录编解码](../frontend/jvm/webgraph/src/main/kotlin/io/johnsonlee/graphite/webgraph/NodeRecordCodec.kt) · [Rust 节点解码](../backend/storage/src/node.rs) · [IR](../ir/graphite_ir.proto)

新增一项事实，要逐一协调生产者类型、交换格式变体、持久化标签与载荷、映射列、属性访问器及公开投影。同名或最终使用相同字节，都不足以使这些定义一致。这是直接的 schema 问题：目前缺少一份统一契约，说明每个参与环节必须传递并公开什么。若替换后各环节仍要手工维护一份枚举，同样的问题还会出现。

### P2. 枚举所有节点不足以列出全部事实

历史上的一张 Signal 图在 IR 中有 10,027 项枚举声明，它们没有对应的 EnumConstant 节点，因而在保存时丢失。原因是收集器从值的出现反推声明清单。当前实现已通过独立的枚举索引修复此故障，同时为旧版 Graph 实现保留回退逻辑。故障已修复，其架构意义仍在：只要契约未涵盖所有事实族，每增加一类元数据，就要另行打通枚举和保存路径。校验和正确、若干节点查询结果正确，都不足以证明仅有声明的事实也被保留下来。[历史故障及修复](apple-frontend-validation.md) · [当前收集器](../frontend/jvm/webgraph/src/main/kotlin/io/johnsonlee/graphite/webgraph/GraphMetadataCollector.kt)

需要区分声明与使用，以及枚举与查找。某个枚举项的构造参数列表为空，仍然是已知的声明；找不到该项则是另一种情况。一个方法可以没有调用者，也可以没有已分析的方法体。这是 schema 层面的清单问题，同时也要求适配器与写入器按清单处理。

### P3. 身份、显示文本与解析结果相互混杂

在 JVM 输入的作用域内，方法可以用声明类、名称和完整 descriptor 标识。该约定不能原样套用于所有格式。Apple 的内部模型保留编译器 USR，但输出的方法引用只含所属对象、名称、参数类型和返回类型。Web 遇到原本相同的方法键时，会给所属对象加上 `#declaration@<position>`。Apple 还为模块顶层调用构造 `<top-level>` 调用者。这些都是为适应公共 descriptor 结构而采取的具体处理，不能据此断言某两个具体声明已经被合并。[Apple descriptor 与调用](../frontend/apple/Sources/GraphiteFrontend/Emitter.swift) · [Apple 符号模型](../frontend/apple/Sources/GraphiteFrontend/IndexModel.swift) · [Web 声明注册](../frontend/web/src/analyzer.ts)

位置也经历了类似的信息缩减。Apple 区分调用出现时使用模块、调用者与被调用者的 USR、文件、行和列；输出的调用点保留 descriptor、行和参数引用。同一行上的不同调用仍可用不同的节点 ID 区分，但仅凭这些已保存字段，无法恢复缺失的编译器身份或列号。

在其他输入格式中，导出符号可以没有已知的源码声明，函数可以没有所属类，一个地址则需要指明映像与坐标系。若把它们一律表示为 JVM 方法，就可能把观察到的名称误认为身份或已解析目标。schema 必须允许这些概念并存，不应迫使适配器编造语义信息。已有显示字符串仍属于兼容性契约。

### P4. 共享字段未必具有相同语义

对已解析的调用，Web 在处理默认参数后记录有效实参。Apple 从匹配到的源码语法中记录实参；没有匹配到语法时也会输出空列表。IR 只存一份有序节点引用列表。仅读取该列表，有时无法区分已知没有实参与未提取实参，也无法区分显式传入的参数与处理后的有效值。[Web 分析](../frontend/web/src/analyzer.ts) · [Web 语义说明](typescript-frontend.md) · [Apple 调用输出](../frontend/apple/Sources/GraphiteFrontend/Emitter.swift)

其他领域也有类似现象。Apple 输出资源键值节点，而 JVM 资源契约允许保留配置文件而不将其内容建成 ResourceValue 节点。Apple 把协议关系投影到现有 EXTENDS/IMPLEMENTS 类型，这种映射不能保留 Swift 的所有协议遵循条件。IR 的值解码器会把显式 null 和未设置的值变体都转换为 Kotlin null。这是解码器的行为，不能据此推断生产者实际输出过未设置的值。[JVM 资源契约](../frontend/jvm/sootup/src/test/kotlin/io/johnsonlee/graphite/sootup/ResourceConfigLinkingTest.kt) · [Apple 资源](../frontend/apple/Sources/GraphiteFrontend/AppleResources.swift) · [IR 值解码](../frontend/jvm/ir/src/main/kotlin/io/johnsonlee/graphite/ir/IrReader.kt)

README 还描述了资源之间的 RESOURCE_CONTAINS 关系，但当前 IR 和关系匹配器中没有相应的种类。这是文档与实现之间需要明确解决的契约缺口，仅统一标签不能决定应如何处理。[README 资源查询](../README.md#query-resources-with-cypher) · [Rust 关系匹配](../backend/cypher/src/engine/matching.rs)

schema 需要精确定义观测、推导事实、字段是否存在，以及集合是否已完整采集。提取更多事实仍是前端的工作。统一标签无法补足输入或分析未提供的证据。

### P5. 来源、语义覆盖与完整性各有局部契约

Graphite 已经有以下机制：

- IR header 含生产者名称及版本、源输入信息和选项，Apple 也将其源码数据流分析范围写入其中。导入命令打印 header 信息，但保存时只传入 Graph；这条路径没有将 header 作为持久化的来源契约传递下去。[生产者](../frontend/apple/Sources/GraphiteFrontend/Frontend.swift) · [导入器](../frontend/jvm/query/src/main/kotlin/io/johnsonlee/graphite/cli/ImportCommand.kt)
- `.graphite` 容器有记录文件大小及哈希的清单、必需文件和校验机制。它描述物理内容，没有声明采集了哪些事实、事实的含义或未知扩展会改变什么。加入 ClassConstant 前后的图都使用节点格式版本 3。旧图中的整数零不能重新解释为已恢复的类字面量。[容器](../backend/storage/src/container.rs) · [类字面量兼容性](webgraph-storage.md#class-literals-node-tag-16)
- 方法体分析完整性记录范围及缺口原因。`/api/schema` 列出现有图中观察到的标签、属性和关系。两者都未提供覆盖全部事实族的通用采集覆盖声明。[分析完整性](analysis-completeness.md) · [Schema 端点](../backend/explore/src/routes.rs)
- 错误处理随数据族而异。已绑定的声明类型数据缺失或损坏时，读取器会报错。分析完整性文件缺失、绑定不匹配或布局不符时，读取器不返回相关证据；绑定匹配后若载荷摘要校验或解析失败，则报错。分支定义数据可能给出警告并返回空定义。Rust 的 `Graph::node` 会把解码错误转成 `None`。不能把这些情况一概视为有效的空结果。[声明类型](../frontend/jvm/webgraph/src/main/kotlin/io/johnsonlee/graphite/webgraph/DeclaredTypeStore.kt) · [分析完整性读取器](../frontend/jvm/webgraph/src/main/kotlin/io/johnsonlee/graphite/webgraph/AnalysisCompletenessStore.kt) · [伴随文件行为](webgraph-storage.md) · [Rust 节点访问](../backend/storage/src/graph.rs)

schema 必须定义每项能力承诺什么，以及缺失、不支持或无效的数据如何影响该承诺。持久化来源、校验字节及传播错误仍需改动实现。图在物理上是否完整、提取覆盖了什么、查询是否执行完毕，是三个不同的问题。

### P6. 图组合缺少共同的产物与系统归属模型

同一 SDK 可以出现在多个服务中，一个服务也可以由多份产物或多张图构成。图名可以在之后指向另一构建。一个包可以容纳多种格式，一个文件也可以包含多个架构切片。类来源、带权产物依赖以及查询结果的图来源已经提供了部分信息，合起来仍不足以说明内容身份、在包内的具体出现、编译上下文、服务版本和环境。

即使没有更丰富的模型，跨图连接今天也已经能用。缺少的是这些跨边界连接代表什么。名称相同或字节相同，单独都不能证明服务身份相同，也不能证明调用了某个特定 handler。从图推导出的拓扑边，也需要与根据路由及提供方证据确认的绑定区分开。这是逻辑模型缺口，填充它还需要单独的提取与解析工作。[现有拓扑](topology-graph.md) · [来源及依赖元数据](../frontend/jvm/core/src/main/kotlin/io/johnsonlee/graphite/graph/Graph.kt)

### P7. 扩展绑定于特定生产者与固定的图词汇

SootUp 已经有通过 ServiceLoader 发现的 `GraphiteExtension` SPI。它的访问器接收 SootClass，因而与该前端耦合。对于新的框架事实，这个 SPI 没有规定可跨前端使用的定义、交换、保存及查询契约。任意增加属性也不足以定义新关系的身份、重复次数、作用域与证据。[现有 SPI](../frontend/jvm/sootup/src/main/kotlin/io/johnsonlee/graphite/sootup/GraphiteExtension.kt)

这一扩展边界原本是合理的产品取舍。支持更多格式与系统语义之后，需要决定哪些扩展可以直接由现有消费者传递，哪些需要新增分析代码。这属于 schema 的职责。发现框架路由或解释新的二进制指令仍属于具体领域的工作。

### 相关工程问题仍在范围内，各有对应的责任层

最初的问题清单包括以下各项。逻辑 schema 应说明它与这些问题的依赖关系，不能因为给出了定义就声称已经修复。

| 问题 | 现有证据与需要区分的情况 | Schema 的职责及其余工程工作 |
| --- | --- | --- |
| 建模有损；混淆事实不存在与未采集 | P2–P5 涵盖已修复的信息丢失、现存的语义缩减，以及局部的完整性机制。 | 定义应保留的事实、含义与覆盖范围；提取准确性和适配器忠实度仍取决于实现。无损重建输入不在目标内。 |
| 增加事实要改多处；文件清单与生产者历史 | 见 P1、P5。已有物理归档清单及 IR 生产者 header，共享语义清单与端到端来源契约仍不完整。 | 为各参与环节及其演进定义共同的语义契约。无需仅为更名而替换现有文件清单。 |
| 保存至源图目录；损坏数据被视为空 | 目录写入器会先删除伴随文件，再收集部分延迟读取的元数据，并就地写入文件。源码检查表明，这里有数据丢失或混入不同代文件的风险；本轮没有重新复现故障。归档输出另有发布保护。 | 定义快照一致性与错误含义。目录安全发布、读取器生命周期和错误传播属于实现修复。[写入器](../frontend/jvm/webgraph/src/main/kotlin/io/johnsonlee/graphite/webgraph/GraphStoreWriter.kt) |
| JVM/Rust 查询与 JSON 漂移 | 一些差异是已记录的一致性缺陷，例如内部单图来源信息；另一些是有意增加的能力，如 Rust 的 `total`。参数错误的响应结构也不同。 | 共享属性及身份定义可减少重复解释。HTTP 错误结构、方言行为与结果序列化仍需要各自的共享契约。[一致性记录](../backend/bench/parity.py) |
| 分页、大范围查询超时及能力发现 | 已有 SKIP/LIMIT、截断信息、取消、超时和 schema 发现。这些机制没有提供稳定的快照游标或通用的提取覆盖发现机制。 | 说明能力和快照的含义。分页协议、查询计划与执行控制仍属服务端职责。[解析器](../backend/cypher/src/parser.rs) · [路由](../backend/explore/src/routes.rs) |
| 进程级 ID 及按最大 ID 分配空间 | Kotlin NodeId 使用进程计数器，构建器偏移表与保存时的邻接结构按最大 ID 加一分配；本轮未量化资源影响。 | 将身份的作用域与物理编号分开。分配和索引布局需另行设计并在有代表性的负载上测量。[ID](../frontend/jvm/core/src/main/kotlin/io/johnsonlee/graphite/core/Node.kt) · [构建器](../frontend/jvm/core/src/main/kotlin/io/johnsonlee/graphite/graph/MmapGraphBuilder.kt) |
| 依赖调度时序的测试和较长的验证周期 | 这是原问题清单中的工程问题，本次评审没有产生新的耗时测量。 | 共享语义用例可以减少重复维护的预期结果。统一 schema 本身不能控制调度或加快验证基础设施。 |
| 缺少通用的框架语义扩展层 | P7 区分现有生产者 SPI 与可跨前端传递的事实契约。 | 定义扩展的含义与保存要求。框架分析及专用展示仍需编写代码。 |

## 3. 由这些问题推导出的设计决策

### D1. 以定义和完整事实清单作为共享边界

数据集声明使用了哪些定义，并枚举其全部语义记录，包括没有使用节点的声明。一项定义由（命名空间、名称、语义版本）标识，规定具名且有类型的角色、存在性与基数规则、身份与相等性规则，并指明所依赖的确切定义。可重复的角色须指明顺序及重复值是否有意义。语义版本标识含义，物理格式版本与生产者版本分别保留。定义与已发布的每个投影版本分别由各自的身份标识，在该身份下不可改变。如果两张图以同一身份发布不同定义，它们的契约便有冲突。可以分别检查各图，但依赖该身份的组合操作必须拒绝冲突，或显式使用有版本的转换；名称写法一致不能作为合并语义的依据。

逻辑值体系涵盖有类型的标量、带作用域的引用、有序集合与具名结构化值。必须保留现有数值类型之间的区别，以及 null、注解映射和枚举引用。字段缺失、显式 null、空集合各有不同含义。仅凭一个字段可选，不能判断它不适用还是未被观察到；当这种区别影响问题时，由定义提供观察状态或另行给出覆盖声明。格式原生的 descriptor 可以保留为有类型的不透明值，并注明其语法。不理解该语法的消费者可以保留这个值，并对它的确切表示进行相等性比较，但不能据此推断类型等价。

每个参与环节都必须能够枚举并传递这些定义和记录。清单由生产者提供，包括只有声明的事实族，以及生产者声称已完整枚举且结果为空的集合。承诺保留事实的环节须能说明输出如何保留了这份清单，以及其中的记录身份、有序值和引用。只重新发现写入器已认识的种类，或只统计节点数与边数，不能证明信息得到了保留。怎样高效核对属于实现设计，无需要求每次查询都核对。对于能用已有值类型和关系表达的事实，新增工作落在事实定义与生产者上，读者、写入器和属性访问器无需各自增加专属分支。消费者提供按定义选择、按角色投影、沿引用连接及计数等通用操作。因此，即使尚无专用分析或 UI，也可以检查新事实。专用运算与优化访问作为显式能力保留。这里确定的是逻辑访问契约，未指定表结构、序列化方式或 Cypher 语法。

定义不含可执行插件。它规定结构与语义，领域算法按其规定产出事实。新的基础值编码、查询运算或解析算法仍可能要求消费者发布新版本。仅给谓词起名不能交付一种新的语义分析。

**例子。** 类字面量的每次出现是一个带有所引用类型 descriptor 的有类型值。它的定义规定怎样公开该值，各参与路径均须传递这个定义和值。文本刚好相同的字符串仍是字符串；导入旧图时，零仍是整数，其历史来源未知。本项改变消除了各环节重复定义传输及属性词汇的工作，从字节码识别类字面量仍由前端负责。这样解决 P1、P2，同时不声称能恢复已丢弃的信息。

#### 一项常规扩展如何经过整条链路

假设一个新的框架规范定义了 `acme.http:request@1`，包含调用点引用、HTTP 动词、路径及有序的参数绑定。每项绑定保留参数位置和值引用，两个位置可以指向同一个值。提取器提供定义、带作用域的出现身份、记录及提取覆盖声明。本例假定通用契约已经支持它需要的所有值类型与结构操作。

| 环节 | 消费者无需为该事实类型单独发布新版本时，应能完成的行为 |
| --- | --- |
| 导入 | 读取提供的定义，校验角色类型及引用作用域，保留请求记录。无需给封闭枚举新增变体。 |
| 保存与重新打开 | 独立于既有节点种类枚举所提交的事实族，保留其身份、值、引用与覆盖。 |
| 通用查询 | 选择该定义，按动词和路径过滤，连接调用点引用，并用已有结构操作返回有序绑定。即使引擎没有针对这个框架的专用逻辑，用户也可以检查新事实。 |
| 导出或复制 | 传递不熟悉的定义及记录，并保留引用。工具若做不到，须拒绝这项要求保留信息的操作。 |

该承诺适用于实现了本提案通用契约的消费者，不适用于今天的 IR v1 或 JSON 导入器。通用契约实现后，这些消费者无需重新构建即可传递本例中的事实。这仍然不能确定目标服务或 handler，需要专用解析器提供相应结论。若需再发布一个公共投影，须声明投影版本并确保所需操作已受支持；不支持的投影不可用，依赖它的查询须被拒绝。既有的 `MATCH (n)`、标签与属性不会因此静默纳入这些记录。

### D2. 区分对象、对象的出现及关于它们的事实

对象的身份限定在作用域内。事实描述对象的属性或关系，也可以引用其他事实。由定义决定哪些参与对象及值足以标识一项事实，以及何时还需要出现标识。不同依据可以支持同一个断言；即使属性值完全相同，多个调用出现仍分别保留。

公共程序词汇涵盖类型声明、可调用成员及存储成员的声明、调用出现、值、局部变量、参数、返回、注解、资源和关系。它们是一组逻辑角色，前端按能力提供。输入不必一律公开类型、所属类、方法体或数据流。独立的元数据清单与节点记录受同一契约约束，无需挤入既有的节点枚举。

| 区分 | 规则 | 所应对的问题 |
| --- | --- | --- |
| 声明 / 出现 | 没有调用者的方法声明、没有常量出现的枚举项都要保留。一个声明可以对应多个观察位置或代码实例。 | P2 |
| 身份 / 显示 | 有可用的原生键时使用带作用域的原生键，否则给出显式的局部身份。名称、签名、descriptor 连同其语法作为属性保留。不能从不完整的显示签名推出身份。 | P3 |
| 引用 / 目标 | 即使没有可用声明，也保留调用点所引用的内容。已解析目标或候选目标另作事实，带上其成立条件。 | P3、P6 |
| 显式实参 / 有效值 | 按不同角色分别记录，保留参数序位和重复引用。缺少实参清单不能声称实参数为零。已有的有效参数投影继续可用。 | P4 |
| 原生事实 / 公共含义 | 保留输入格式自身的观察。只有观察能够支持公共解释时才发布该解释，并保留前提。对 Swift 协议遵循关系的投影无需声称它具有 Java 继承语义。 | P4、P7 |

对于现有 JVM 图，方法声明键包含所属类、名称与完整 descriptor，其中包括返回类型。已有调用点、常量等节点保留其快照内的出现 ID。按类名和成员名查注解仍是既有查找方式，不能凭空拥有来源记录所缺少的重载区分精度。原生符号可以没有已识别的函数体；顶层可调用对象也无需虚构一个所属类。

### D3. 区分内容身份、解释上下文、图身份与服务身份

| 对象 | 身份与关系 |
| --- | --- |
| 产物内容 | 一个输入文件或有清单的集合。摘要算法、所涵盖的内容范围与规范化规则相同时，摘要相等可以作为内容相等的依据。成员的摘要不能用于判定其整个容器相同。缺少相应证据时使用局部身份。 |
| 产物条目 | 内容在容器中的一次出现，带有父容器和成员的位置或名称。两个包可以经由两个不同条目引用相同内容。 |
| 表示 | 在特定输入或编译上下文中对内容的解释，可以依赖多份输入。Mach-O 的各个切片有各自的解释范围；同一 Swift 源码在不同目标下编译，也有不同的解释范围。 |
| 位置 | 包含表示、坐标系、必要的所属对象及点或范围。坐标系定义单位和原点。源码位置、方法内字节码偏移、节偏移、文件偏移和映像地址分别表示。它们之间的映射是显式事实，可以只在部分位置上有定义。 |
| 快照 | 一份具体图输出，包括此次分配的标识。在该快照内，局部节点 ID 才能标识一次出现。输入和选项相同不足以证明输出 ID 相同。已有注册图名继续充当公开句柄。 |
| 服务版本与系统视图 | 服务有自己的身份，已知时附带版本；视图选择快照、服务与产物的归属、服务清单及静态环境输入。未知版本保持未知。一个服务可对应多张图，多个服务也可复用同一份内容。 |

只有问题依赖某种上下文时，才要求提供它。导入旧图无须编造原始构建执行或产物层级。按现有方式注册图，仍可提供一张图对应一个服务的映射。

内容相等允许复用从内容得到的观察；依赖上下文的结论还取决于编译、链接或路由输入。跨快照关联要指明含义，例如内容相同、调试信息对应或仅在特定条件下成立的 API 绑定。这些关联不会合并节点的出现。内部表示若重新编号，必须保留引用与既有的公开身份投影。这处理 P3、P6，物理 ID 的分配方式仍留待设计。

### D4. 让来源和覆盖声明随所限定的事实传递

若信息可得，一次提取应记录生产者及其版本、输入和生效的选项。直接观察指明提取执行，可选择附加输入定位。推导结论指明规则及版本、前提事实与解释上下文。默认依据可以在批次或作用域内共享，因此契约不要求每个节点各存一个来源对象。多项独立观察可以支持同一事实；冲突的结论各自保留依据。

在快照或系统视图内，覆盖声明限定到事实定义、所选对象域和提取条件，分别说明已经完整枚举、只枚举了一部分且有已知缺口，或覆盖未知。较小范围的例外可以限定更广的声明。现有的方法体完整性是该契约的一项来源，应继续保留，不能外推到无关事实。

需要分别回答三个问题：

1. **已保存的图含有什么？** 普通 Cypher 继续查询图中实际记录的内容。返回零行 ResourceValue 可以是关于这张图的精确答案。
2. **这能证明输入或系统的什么情况？** 要证明配置键不存在，需要覆盖该文件中键的提取；要证明没有其他调用者，需要覆盖相关服务、调用点和解析域。
3. **查询是否完成？** 即使输入事实完整，超时、取消或结果消费被截断，都不能支持穷尽结论。

未来的读取器可以在不了解专用解释的情况下，按结构传递新的定义。它可以执行其依赖都得到支持的操作。如果不支持的语义可能影响所选答案，就必须拒绝该操作；无法隔离这种依赖时则拒绝整张图。以保存信息为目的的保存或导出必须保留语义清单以及不熟悉的记录的身份与引用；若重新映射 ID，映射也必须保持一致。做不到时须明确拒绝；静默丢弃未知事实不算成功往返。显式选择有损投影时，必须说明省略了什么，且不能继承针对这些省略内容的完整覆盖声明。

某项已声明能力依赖的数据损坏，属于完整性故障，不能解释为提取覆盖未知或有效的空集合。可以重建的索引损坏时，可回退到完好的基础事实。历史上缺失的证据仍是未知。对旧路径实施更严格的错误处理属于需要评审的显式兼容性变更，不能作为引入模型的附带结果。这处理 P5；校验和、安全发布及错误传播仍需在实现中落实。

### D5. 将公开投影与底层事实清单分别定义

现有公开图是兼容性投影，其定义规定标签与别名、属性、边的方向与种类、重复次数以及缺失值行为。现有 Kotlin 访问器、Cypher、REST、MCP 与 Explorer 都必须保留已支持的行为。一条新的声明或来源事实，不会自动给 `MATCH (n)` 增加一行、给 `keys(n)` 增加一个键，或给现有遍历增加一条关系。

跨格式的公共视图仅公开确实共享的含义。具体格式或框架的语义规范集（profile）负责更专门的定义，并声明哪些投影有证据支持、可进入公共视图。各实现以共享定义及投影规则为语义依据。常规映射需能直接使用这些依据，或由其生成；在每个引擎中再复制一份手写列表，会让 P1 原样保留。领域推理留在生产者或分析器内，其结论作为事实输出。

即使存在解析结果、服务清单与来源事实，也不能让普通查询因此必须执行解析、加载清单或遍历来源。依赖这些工作的查询显式选择更丰富的视图。新的公开投影可以提供附加能力，同时保持旧查询的解释。定制可视化仍需展示层工作；统一 schema 也不会使两套引擎的执行或 HTTP 协议自动一致。这处理 P1、P4、P7，同时保留生产行为。

## 5. 在已有跨图查询之上分析整个系统

保留当前的并集查询与 fanout 模式、`graphId` 以及每行的 `$metadata.graphIds`。保留拓扑规则、C4 与端点分组。从 RPC adapter 类名中提取目标服务的旧规则仍可使用，其结果仍以规则声明的线索为依据。如果用户的问题需要更强的结论，模型可补充归属与带成立条件的事实。

设 orders 与 billing 都打包了同一个 payments SDK。orders 有两个调用点 C7、C8，通过别名 `pay` 请求 HTTP `POST /refunds`。billing 的 B2 已知请求什么操作，但目标未解析。所选 staging 视图包含这些服务及未采集请求的 legacy-worker。要问的是，在该视图中，哪些调用点能够静态绑定到 payments 的 handler H1。

以下事实分别成立，也可独立检查：

| 事实 | 能证明什么 |
| --- | --- |
| 包内成员关系与服务归属 | 每次出现属于哪个选定的服务版本。只打包 SDK 不能证明存在退款调用。 |
| C7/C8 发出的请求 | 调用的具体出现，并有协议、操作与观察到的目标引用。 |
| staging 路由事实 | 在声明的路由规则下，别名 `pay` 有哪些适用的目标。 |
| 提供方事实 | 选定的目标服务版本公开哪些操作以及相应的 handler。 |
| 候选或绑定事实 | 解析器得出的结论。其依据包括请求、路由、提供方、规则与版本、上下文及相关覆盖。 |

本例的解析器按别名找到目标，再匹配协议、动词与路径。它的范围排除了运行时覆盖、回退与重写。确认唯一绑定要求完整枚举适用路由与提供方、评估优先级规则，并且最终恰有一个可行的 handler。这一定义以本例的路由模型为条件；在开放的候选域中，只观察到一个候选仍不充分。

如果 C7、C8 都绑定到 H1，则报告来自 orders 的两个已确认调用点。由于 B2 与 legacy-worker 仍有缺口，系统总数未知。如果候选集合同时含 H1 和 H2，则两者都保留，并报告 H1 可能受影响，不宣称唯一绑定。缺少路由表时结果未决；完整的适用路由表明确没有目标时，则可以按该规则排除该调用点。要得到精确总数，还要求服务清单完备，且对每个相关服务的请求都有充分覆盖。

不同环境可能有不同的适用路由，绑定也可能随之改变，而观察到的调用点仍然相同。两个环境仍可以解析到同一个 handler。多个服务复用同一库时，可复用从内容提取的事实，但要保留每个服务中的具体出现及其上下文结论。跨服务的操作绑定可以支持操作级影响分析。字段级数据流还需要序列化与解码之间的对应关系；仅有端点相等不足以补出这样的对应。

这为 P6 中一部分跨图连接补充了缺失的含义。协议和框架的提取器、解析器仍需实现。模型没有声称能从静态配置重建完整的运行时系统。

## 6. 用其他输入格式检验同一模型

### IPA 与 Mach-O

IPA 中的应用、扩展与 framework 都是容器条目。其可执行内容可产生 Mach-O 表示，各架构切片有独立的位置域。包内成员事实说明实际分发了什么，装载命令给出库请求，符号表提供定义及未解析的引用。即使不能分析调用，这些事实也各有用途。

对于 `@rpath/Pay.framework/Pay` 这样的请求，候选解析取决于发出请求的映像、架构、搜索上下文，以及包内或外部的候选项。匹配到导出符号本身无法定位某个调用点或证明实际执行。移除 Pay 后，请求仍存在，包内候选消失。新增无关的 framework 只会改变清单，不会产生从应用到它的调用或依赖。

若架构及构建身份能证明对应关系，匹配的 dSYM 可以为相应表示补充信息。文件同名本身不够。剥离符号后的映像仍可回答覆盖范围内的装载依赖问题，而函数名、源码位置可以未知。D2–D4 无须编造方法或完整数据流即可表达这些区别。[Apple build UUID 说明](https://developer.apple.com/documentation/technotes/tn3178-checking-for-and-resolving-build-uuid-problems)

### 独立或打包的 ELF

一项 ELF 重定位可以指出在 `.text+0x10` 处有对 `pay` 的引用。若 `.text` 从文件偏移 `0x40` 开始，则该处的文件偏移是 `0x50`；文件偏移 `0x10` 指向另一个字节。位置需要指明表示与坐标系。可重定位目标文件不一定提供最终映像地址，也不一定说明哪个库会满足该引用。

可装载映像还可以包含零初始化的内存区，其中没有对应的文件字节。因此，位置间的对应必须允许只在部分位置上有定义。同一份 ELF 作为独立文件和作为 APK 成员输入时，可以复用从内容得出的动态依赖；包内出现和库解析上下文则分别保留。[ELF 重定位](https://gabi.xinuos.com/elf/06-reloc.html) · [ELF 程序装载](https://gabi.xinuos.com/elf/07-pheader.html)

一个有用的 ELF 或 Mach-O 前端最初可以仅发布清单、装载依赖与符号，并通过覆盖声明注明范围。它不应为了凑齐一张通用节点清单而虚构局部变量、参数或数据流。格式自身的新事实按 D1 传递；提取、反汇编及语义恢复仍是独立能力。

## 7. 提案能解决什么，代价是什么

| 问题 | 决策与预期结果 | 其余工作或限制 |
| --- | --- | --- |
| P1：重复定义 | D1/D5 将事实结构与投影纳入共享契约，常规新事实可被传递和检查，无需所有环节同步增加专用分支。 | 各环节要一次性实现通用支持，领域运算与专用展示仍需编写代码。 |
| P2：节点清单以外的事实 | D1/D2 让声明及元数据清单可独立于使用和遍历而存在。 | 既有适配器仍须如实枚举；旧图缺失的信息需要新的输入证据。 |
| P3：身份和表示被缩减 | D2/D3 保留原生身份、引用、上下文和位置，无需赋予它们虚构的 JVM 含义。 | 生产者必须输出可获得的上下文；判断两个独立输出中的对象相同，需要证据。 |
| P4：含义混用 | D2/D4/D5 区分观察、解释与覆盖，同时保留旧投影。 | 公共视图可以只公开原生语义规范集（profile）中的部分含义。新增提取能力仍需实现。 |
| P5：混淆不支持、缺失、损坏与不完整 | D1/D4 区分语义能力、来源、完整性依赖及查询完成情况。 | 读写器和服务 API 需实际执行这些规则。安全发布属于独立的工程工作。 |
| P6：系统归属 | D3/D4 在跨图分析中保留产物的每次出现、服务版本、环境与绑定前提。 | 服务清单、协议知识及配置需要提供或提取。 |
| P7：生产者专属扩展 | D1/D5 允许具体格式或框架的规范引入有类型的事实，并声明公共投影。 | 定义事实不会自动实现提取器、解析器或 UI。 |

这些选择有实际代价。除了已有的优化路径，还需实现通用的结构访问。定义与投影需要明确由谁维护语义，以及如何管理版本。更精确的身份与证据会增加需要管理的信息，即使这些信息可以在作用域内共享。覆盖声明要求生产者交代采集缺口。视图的精度受证据限制，因此一些跨格式问题仍会合理地保持未决。

三条看似省事的路都没有触及根因。只给现有 JVM 类型改名，P3 的 descriptor 限制依旧。增加任意属性映射，事实身份、独立清单及覆盖仍没有定义。只替换物理格式，生产者和查询实现仍可能给同一记录赋予不同含义。反过来，把每种输入都转换成完整的编译器 IR，会超出 Graphite 的定位，也给本来有用的局部二进制分析带来不必要的门槛。

评审首先应判断，P1–P7 是否解释了真实的扩展难点与正确性问题，D1–D5 是否能在保留现有产品能力的同时消除相应根因。尤其要排查以下情况：没有使用点的声明仍无法保存，未知事实可能静默消失，旧查询平白多了结果行或改变含义，或者没有足以区分目标的前提也能断言服务绑定。出现其中任何一项，都应否决本模型。

本稿不宣称已有新的实现、基准性能改进或完整的输入重建能力。后续物理与实现设计必须保留现有正确性、可用性与资源约束，并采用仓库规定的代表性多图验收要求。后续工程不能代替本轮对逻辑问题的判断。[范围与非目标](universal-schema-scope.zh.md) · [工程约束](../CONVENTIONS.md)
