只对既有冻结 main 三份录制做离线分析；没有修改生产代码、启动 JVM、重新采样或重跑候选。原始输入是 `/private/tmp/graphite-distinct-phase-details/phase-{1,2,3}.json`，输入 SHA-256 和全部精确纳秒保存在 `summary.json`。`python3 analyze.py` 可重算。

三份录制中，targeted 最长两次图级调用的区间均不重叠。初始选择阶段约 97% 的有调用区间只有一个图级调用。dense 来源补全则约 95–97% 的有调用区间同时存在两个图级调用。四个不同 graph worker 名称出现过，不能把历史上出现的线程总数误读成四个同时运行的图级调用。

这改变了删池前的检查重点：两条决定旧 34 条 P95 的路径具有不同的图级重叠结构。targeted 需要减少稀疏命中图的实际扫描；dense 还需要减少后续图的来源查找工作。不能从 targeted 图级重叠少，推断删除所有 CallSite 线程池都会改善两条路径。

## 解释边界

- 图级调用区间包含执行、被调度器挂起、子任务等待及 tracing 成本；同时存在不等于同时占用 CPU。
- 子图内部的 CallSite segment worker 没有独立计入这个并发数。因此 targeted 平均 1.03 不代表只有一个 CPU 在工作。
- 调用时长总和仅用于重叠守恒，不能充当串行版本延迟、CPU 时间或潜在加速比。删除线程会改变这些时长。
- `durationByActiveGraphCallsNanos[0]` 只统计首个调用开始至最后调用结束之间的空隙；不是整条查询的所有其余时间，也不能全部归为调度开销。
- 没有图 ID 参数的 trace 不用于把某个长区间指认到某个具体图。单图/多图实际命中分布来自另行核对的完整参考扫描。
- 三份诊断录制不构成候选性能门槛数据，不改变任何此前接受/拒绝决定。

## 机械核对

每次调用的绝对开始/结束差等于其记录 duration；同线程同阶段无区间重叠；扫描线并集逐个等于原分析器记录的 phase union；并发数乘区间时长的总和等于各调用 duration 总和。每个查询的初始、补来源与其余区间合计等于 execute 窗口，execute 加 trace 外差值等于 TSV 延迟。全部 9 条 DISTINCT 记录、576 个图级阶段调用通过。
