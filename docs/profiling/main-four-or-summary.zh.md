# A OR B OR C OR D：覆盖与已验证的瓶颈

纯四词 OR 已作为独立查询类型测量。每个关键词查 caller/callee 的 class/name
四个属性，编译为 16 项 `DirectStringDisjunction`。每个词都有只命中它的节点，
因此四个分支都不可省略；同一节点命中多个词也不能重复输出。

## 冻结 main 的覆盖和耗时

基线为 `4e328b0109e13c896b74004823fb049fcb19251a`。真实输入是 Android 14、
Tika 2.9.2、Hive 4、Kotlin compiler 2.0.21 各 16 个持久化分片，共 64 图、
5,046,935 个 CallSite；不是 64 个独立应用。以下六组各含普通投影与 DISTINCT，
共 12 条，属于补充的 36 条清单，与历史 34 条性能 gate 分开记录。

| LIMIT 前完整命中分布 | 匹配节点数 | 普通投影经验 P95 | DISTINCT 经验 P95 |
|---|---:|---:|---:|
| 单图，位置 0 | 704 | 17.438 ms | 152.652 ms |
| 单图，位置 31 | 2,646 | 94.437 ms | 151.192 ms |
| 单图，位置 63 | 299 | 151.125 ms | 150.579 ms |
| 两图，位置 0 和 63 | 972 | 17.361 ms | 151.402 ms |
| 55 图 | 50,461 | 39.582 ms | 152.804 ms |
| 全部 64 图：`get OR set OR read OR write` | 2,455,554 | 16.458 ms | 185.749 ms |

每条查询在 20 个独立 JVM 中各测一次，按该查询的第 19 个升序耗时计算经验 P95；
每条查询前清理字符串索引，JIT 和 OS 页缓存不重置。20 个样本不保证稳定性。
全部 720 次查询核对了完整值、顺序和来源图，输入文件前后哈希一致。
不同分布使用不同关键词，不能把全部差异只归因于图的位置。

命中图数统计完整条件在 LIMIT 之前的集合。普通投影可能由首图填满 200 行；
DISTINCT 还须查明其他图是否包含这 200 个元组，补全来源，不能因此跳过后续图。

## 优化机会及其证据边界

55 图纯 OR 的冷索引 DISTINCT CPU 录制中，11,183 / 13,830 个样本（80.86%）
包含完整索引校验调用栈；94.24% 的采样分配权重落在 Integer/Long 装箱叶子。
通用 `ExpressionEvaluator.evaluate` 样本为零。这里的可验证机会是降低完整
校验的逐元素开销，保留 CRC、范围和物理顺序检查、预算及取消语义。
这些是栈样本和采样分配权重，不是延迟占比，也不能推广为其他五种分布的热点。

Attempt 137 已实际验证减少回调装箱：局部采样和冷查询耗时改善，但完整 CI
出现重复 Method4 CPU 回归，因此生产改动已回退。它仍是已定位的成本，
尚未成为可保留的优化。

同一查询热索引的应用 CPU 样本中不再出现完整校验；匹配、posting 查找、
集合检查和结果处理都有样本，尚不能断言一个普遍的热态瓶颈。
冷转热的差值不是新代码收益。`(A AND B) OR (C AND D)` 的全节点表达式
求值热点属于另一条路径，不能用它解释纯 OR 或预测纯 OR 的收益。
